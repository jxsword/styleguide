## 简介

本文档提供了一组在设计新的
XML 文档格式时通用的准则（在某种程度上也适用于 XML 文档本身；参见
[文档实例](#s11)）。文档格式通常既包含形式化的部分
（DTD、模式），也包含以规范性的英文散文表述的部分。

这些准则适用于新的设计，并不打算强制对既有设计做
追溯性的改动。在评审包含新文档格式的设计文档
时，应考虑这些准则，但并非要宣称一种
“XML 可读性”体制。在参与创建公开或私有的
文档格式设计时，这些准则可能有帮助，但不应
支配团队的共识。

本指南面向的是供机器生成和消费、而非供人类阅读的
XML 设计。其规则*不适用*于
诸如 XHTML（应尽可能像 HTML 那样排版）或 ODF
这类旨在表达富文本的格式。若文档包含以 XHTML
或其他富文本格式嵌入的内容，但同时也包含纯
机器可解释的部分，则这些部分 SHOULD 遵循本风格
指南。它也不影响
由 proto buffers 转换、或通过其他类型的
格式转换而创建的 XML 文档格式。

大多数准则都附有简短的理由。它们与本文档保存在一起，
以期不会过时，但它们
不被视为规范性的。

本文档中使用的术语 MUST、MUST NOT、SHOULD、SHOULD NOT 和 MAY
其含义遵照 [RFC 2119](https://www.ietf.org/rfc/rfc2119.txt)。

## 设计还是不设计，这是个问题

1.  尽可能尝试复用已有的 XML 格式，尤其是那些
    允许扩展的格式。创建全新的格式只应在
    审慎考虑之后进行；请先阅读
    [Tim Bray 的警告](https://www.tbray.org/ongoing/When/200x/2006/01/08/No-New-XML-Languages)。
    尽量让你的格式得到广泛评审，如可能，也应包括来自
    组织外部的评审。\[*理由：* 新文档格式是有成本的：它们
    必须被评审、被编写文档，并被用户学习。\]

2.  若要复用或扩展已有格式，请*合理*地使用
    规定的元素和属性，尤其是那些必需的。
    不要彻底改变它们的用途，但不妨看看能否以
    创造性的方式加以利用，前提是默认语义不适用。作为最后的手段，
    当格式要求某个元素或属性、但它并不
    适合你的使用场景时，可用某个固定字符串作为其值。
    \[*理由：* 复用标记是好事，滥用标记是坏事。\]

3.  扩展格式时，请沿用已有格式的隐含风格，即使
    它与本指南相抵触。\[*理由：* 一致性。\]

## 模式

1.  文档格式 SHOULD 使用模式语言来表达。\[*理由：*
    清晰且可被机器校验。\]

2.  模式语言 SHOULD 采用 [RELAX NG](http://www.relaxng.org/)
    的[紧凑语法](http://www.relaxng.org/compact-tutorial-20030326.html)。
    可在模式中嵌入 [Schematron](https://www.schematron.com/) 规则，以便
    进行更精细的控制。\[*理由：* RELAX NG 是最
    灵活的模式语言，对设计几乎不施加任意限制。
    紧凑语法相当易读易学，并且在需要时可以
    与 XML 语法一对一地相互转换。Schematron 能很好地处理
    任意的跨元素与跨属性约束。\]

3.  模式 SHOULD 采用
    ["Salami Slice" 风格](https://www.xfront.com/GlobalVersusLocal.html#SecondDesign)
    （每个元素一条规则）。模式 MAY 采用
    ["Russian Doll" 风格](https://www.xfront.com/GlobalVersusLocal.html#FirstDesign)
    （模式形似文档），前提是它们简短而简单。
    ["Venetian Blind" 风格](https://www.xfront.com/GlobalVersusLocal.html#ThirdDesign)
    （每种元素类型一条规则）不适用于 RELAX NG，SHOULD NOT 使用。

4.  SHOULD 提供正则表达式，以协助校验复杂的
    值。

5.  MAY 提供 DTD 和／或 W3C XML Schemas，以便兼容既有的
    产品、工具或用户。\[*理由：* 我们无法一蹴而就地
    改变世界。\]

<a id="s3"></a>

## 命名空间

1.  元素名 MUST 位于某个命名空间中，除非是在扩展既有的
    不使用命名空间的文档类型。SHOULD 使用默认命名空间。
    \[*理由：* 无命名空间的文档已经过时；每一组
    名称都应属于某个命名空间。使用默认命名空间可提升
    可读性。\]

2.  属性名 SHOULD NOT 位于命名空间中，除非它们来自
    外部文档类型，或打算用于外部文档类型。
    \[*理由：* 命名空间中的属性名必须始终带有前缀，
    输入起来很麻烦，也不易阅读。\]

3.  命名空间名是 HTTP URI。命名空间名 SHOULD 采用
    `https://example.com/whatever/year` 的形式，其中 *whatever* 是
    基于服务或文档类型名称的唯一值，*year* 是
    命名空间创建的年份。还可以有额外的 URI 路径部分位于
    *year* 之前。\[*理由：* 既有惯例。给出年份便于
    将来可能复用代码名称。\]

4.  命名空间 MUST NOT 被更改，除非特定元素
    或属性的语义发生了极其不兼容的变化。\[*理由：*
    更改命名空间需要改动所有客户端代码。\]

5.  命名空间前缀 SHOULD 简短（但不要短到可能与
    其他项目冲突）。单字母前缀 MUST NOT 使用。
    前缀 SHOULD 只包含小写 ASCII 字母。\[*理由：* 便于
    输入，且不存在编码兼容性问题。\]

<a id="s4"></a>

## 名称与枚举值

**注意：** “名称”指元素、属性和枚举
值的名称。

1.  所有名称 MUST 使用 lowerCamelCase。也就是说，它们以
    首字母小写开头，随后名称中的每个新单词都以
    大写字母开头。\[*理由：* 采用单一样式可带来一致性，
    这在引用名称时很有帮助，因为大小写形式已知，
    无须记忆。它与 Java 风格一致，其他语言
    则可通过自动的名称转换来处理。\]

2.  名称 MUST 只包含 ASCII 字母和数字。\[*理由：* 便于
    输入，且不存在编码兼容性问题。\]

3.  名称 SHOULD NOT 超过 25 个字符。应通过
    设计简洁且信息量充足的名称来避免过长的名称。若某个名称只有
    变得晦涩才能保持在此限制内，则 SHOULD 忽略该限制。\[*理由：*
    过长的名称使用起来不便，且需要额外的带宽。\]

4.  已发布的标准缩写，若足够知名，MAY 用于
    构造名称。临时拼凑的缩写 MUST NOT 使用。
    出于 camel-casing 的目的，首字母缩略词 MUST 视为普通单词：informationUri，
    而非 informationURI。\[*理由：* 某个缩写对某一
    群体而言众所周知，对需要使用同一文档格式的
    其他人却往往难以理解（他们倒是理解全称）；把首字母缩略词
    当作单词，更容易看清单词的边界。\]

<a id="s5"></a>

## 元素

1.  所有元素 MUST 只包含空内容、字符内容或
    子元素。混合内容 MUST NOT 使用。\[*理由：* 许多 XML 数据
    模型不能正确处理混合内容，使用它会使元素
    依赖于顺序。一如既往，文本格式不受此规则约束。\]

2.  仅仅用于包裹重复子元素的 XML 元素 SHOULD NOT 使用。
    \[*理由：* Atom 中不使用它们，且它们毫无增益。\]

<a id="s6"></a>

## 属性

1.  文档格式 MUST NOT 依赖起始标签中属性的顺序。
    \[*理由：* 很少有 XML 解析器会报告该顺序，而且它不是
    XML Infoset 的一部分。\]

2.  元素 SHOULD NOT 被过多的属性所累（经验法则是
    不超过 10 个）。应改用子元素来封装密切
    相关的属性。\[*理由：* 这种做法保留了 XML 通过元素提供的
    内建可扩展性，并且有助于在规范演进时
    提供向前兼容。\]

3.  属性 MUST NOT 用于承载其中换行符
    有意义的值。\[*理由：* 符合规范的 XML 解析器会把这类换行符
    转换为空格。\]

4.  文档格式 MUST 允许在属性值两侧使用单引号
    或双引号。\[*理由：* XML 解析器不会报告二者的差异。\]

<a id="s7"></a>

## 值

1.  数值 SHOULD 为 32 位有符号整数、64 位有符号整数或
    64 位 IEEE 双精度浮点数，全部以十进制表示。它们对应于 XML
    Schema 类型 `xsd:int`、`xsd:long` 和 `xsd:double`。若
    个别情况下确有需要，`xsd:integer`（无限精度整数）值
    MAY 也可使用。\[*理由：* XML Schema 中的数值类型实在太多，
    这些类型提供了一个合理的子集。\]

2.  布尔值 SHOULD NOT 使用（改用枚举）。若必须
    使用，则它们 MUST 表示为 `true` 或 `false`，对应于
    XML Schema 类型 `xsd:boolean` 的一个子集。`xsd:boolean` 的
    替代值 `1` 和 `0` MUST NOT 使用。\[*理由：* 布尔参数
    不可扩展。允许数值所带来的额外灵活性并未
    被任何解析器抽象掉。\]

3.  日期应使用
    [RFC 3339](https://www.ietf.org/rfc/rfc3339.txt) 格式表示，它是
    ISO 8601 格式和 XML Schema `xsd:dateTime` 格式的子集。SHOULD 使用 UTC 时间
    而非本地时间。\[*理由：* 日期格式与时区实在太多，
    不过也应承认，有时本地时间
    会保留重要信息。\]

4.  字符内容和属性值中 SHOULD NOT
    使用嵌入语法。值中含有语法意味着 XML 工具基本无用。诸如
    日期、URI 和 XPath 表达式之类的语法属于例外。\[*理由：* 用户
    应能仅用 XML 解析器处理 XML 文档，而无须
    额外的专用解析器，这类解析器很容易出错。\]

5.  小心处理值中的空白。XML 解析器不会剥离元素中的空白，
    但会把属性中的换行符转换为空格。不过，
    应用框架可能会进行更激进的空白剥离。你的
    文档格式 SHOULD 就空白剥离给出规则。

<a id="s8"></a>

## 键值对

1.  简单的键值对 SHOULD 用空元素表示，该元素的
    名称表示键，并由 `value` 属性承载值。
    带有 `value` 属性的元素 MAY 还可带有 `unit` 属性，
    用于指定测量值的单位。对于物理量测量，
    [国际单位制](https://en.wikipedia.org/wiki/International_System_of_Units)
    SHOULD 被使用。\[*理由：* 简洁且设计一致。把值放在属性中
    会对用户隐藏它，因为只显示值而不显示键
    并没有用处。\]

2.  若可能的键数量非常大或没有上限，键值对
    MAY 用单个通用元素表示，它带有 `key`、`value`，
    以及可选的 `unit` 和 `scheme` 属性（用于区分
    来自不同域的键）。在这种情况下，还应提供
    （不一定在同一文档中）一份带有人类可读解释的键列表。

<a id="s9"></a>

## 二进制数据

**注意：** 对于是否应将二进制数据
作为 XML 文档的一部分，并没有硬性规定。若它太大，
或许更好的做法是链接到它。

1.  二进制数据 MUST NOT 直接原样包含在 XML 文档中，而 MUST
    使用 Base64 编码。\[*理由：* XML 不允许
    任意的二进制字节。\]

2.  Base64 所要求的换行 MAY 省略。\[*理由：* 这些换行
    意在让纯文本行保持简短，但 XML 并非真正的
    纯文本。\]

3.  可向该元素附加名为 `xsi:type`、值为 `xs:base64Binary` 的属性，
    以表明正在使用 Base64 格式。\[*理由：*
    不透明的二进制大对象应附有解码说明。\]

<a id="s10"></a>

## 处理指令

1.  除为规定纯局部的处理约定外，MUST NOT 创建新的处理指令，
    并且 SHOULD 完全避免使用。
    已有的标准化处理指令 MAY 使用。\[*理由：*
    处理指令难以妥帖地纳入 XML 数据模型，而且总可以
    用元素替代；它们之所以存在，主要是为了避免破坏
    向后兼容性。\]

<a id="s11"></a>

## XML 文档实例的表示

**注意：** 这些要点仅是指导原则，因为由程序创建的
实例的格式往往不受程序员控制（例如，当
使用 XML 序列化库时）。*在任何情况下* XML 解析器都
不应依赖这些准则被遵循。请使用标准的 XML 解析器，
而非自行拼凑的权宜之计。

1.  所使用的字符编码 SHOULD 为 UTF-8。例外情况应需要
    极其有力的理由。\[*理由：* UTF-8 通用且
    被广泛使用。\]

2.  在可能的情况下，命名空间 SHOULD 在文档的根元素中声明。
    \[*理由：* 清晰且一致。\]

3.  命名空间 URI 到前缀的映射 SHOULD 在整个
    文档中保持不变，并且 SHOULD 也用于设计的文档中。
    \[*理由：* 清晰且一致。\]

4.  对于标准命名空间，应使用众所周知的前缀，例如 html:
    （用于 XHTML）、dc:（用于 Dublin Core 元数据）和 xs:（用于 XML Schema）。
    \[*理由：* 人类可读性。\]

5.  标签中 SHOULD NOT 使用多余的空白。在起始标签中的每个
    属性前使用一个空格；若起始标签过长，该空格 MAY
    用换行符替代。\[*理由：* 一致且简洁。\]

6.  空元素 MAY 表示为空标签，或表示为紧跟
    结束标签的起始标签。任何应用都不应区分
    这两种格式。\[*理由：* XML 解析器并不区分
    它们。\]

7.  文档 MAY 使用 2 空格缩进对子元素进行美化打印。
    包含字符内容的元素 SHOULD NOT 换行。
    长的起始标签 MAY 在除最后一个属性值之外的
    任意属性值之后用换行断开（可带额外缩进）。\[*理由：*
    与我们的风格大体兼容。换行字符内容会影响其
    值。\]

8.  属性值 MAY 使用引号或
    撇号包围。规范 MUST NOT 要求或禁止使用其中
    任一种形式。可自由使用 `&apos;` 和 `&quot;` 来转义各类引号。
    \[*理由：* 没有 XML 解析器会报告这一区别。\]

9.  注释 MUST NOT 用于承载真实数据。注释 MAY 用于
    在手写的 XML 中容纳 TODO。在公开传输的文档中
    SHOULD NOT 使用注释。\[*理由：* 注释常常被
    解析器丢弃。\]

10. 若仍然使用注释，它们 SHOULD 只出现在文档
    序言或包含子元素的元素中。若需要美化打印，
    请像元素一样美化打印注释，但要做换行处理。
    注释 SHOULD NOT 出现在包含字符内容的元素中。
    \[*理由：* 注释内部及周围的空白能提升可读性，但
    把注释嵌入字符内容会让人搞不清哪些
    空白属于、哪些不属于内容。\]

11. 注释 SHOULD 在 `<!--` 之后、`-->` 之前留有空白。
    \[*理由：* 可读性。\]

12. MAY 使用 CDATA 段；它等价于使用 `&amp;` 和
    `&lt;`。规范 MUST NOT 要求或禁止使用 CDATA 段。
    \[*理由：* 很少有 XML 解析器会报告这一区别，而且
    CDATA 与文本的组合往往也会被报告为单个对象。\]

13. 除 XML 标准实体引用 `&amp;`、
    `&lt;`、`&gt;`、`&quot;` 和 `&apos;` 之外的实体引用 MUST NOT 使用。
    字符引用 MAY 使用，但首选实际字符，除非
    字符编码不是 UTF-8。一如既往，文本格式不受
    此规则约束。

<a id="s12"></a>

## 元素与属性

**注意：** 对于何时使用属性、何时使用元素，并没有
硬性规定。以下是设计者
应考虑的一些因素；此处不给出理由。

<a id="s12.1"></a>

### 一般要点

1.  属性比元素更具限制性，而所有设计都包含某些
    元素，因此全用元素的设计最为简单——但这并不等同于
    最好。

2.  在树状数据模型中，元素在内部通常表示为
    节点，它比用于表示属性的字符串占用更多内存。
    有时节点属于不同的应用特定类，在许多语言中
    表示这些类也会占用内存。

3.  在流式处理时，元素一次处理一个（甚至可能逐块
    处理，取决于你所用的 XML 解析器），而某个元素的
    所有属性及其值会一次性报告，这会消耗
    内存，尤其当某些属性值很长时。

4.  元素内容和属性值都需要适当地转义，
    因此转义不应成为设计中的考量因素。

5.  在某些编程语言和库中，处理元素更容易；
    在另一些中，处理属性更容易。当心把处理的难易
    当作评判标准。尤其是 XSLT 能以同等的
    便易程度处理两者。

6.  若某份数据通常应展示给用户，请考虑使用
    元素；否则请考虑使用属性。（这条规则常常因
    某种原因而被违反。）

7.  若你在扩展已有模式，请比照该模式中
    的做法来处理。

8.  合理的模式语言，即 RELAX NG 和 Schematron，对元素
    和属性一视同仁。较老、较粗糙的模式语言，如 DTD
    和 [XML Schema](https://www.w3.org/TR/2004/REC-xmlschema-0-20041028/)，往往
    对元素提供更好的支持。

<a id="s12.2"></a>

### 使用元素

1.  若某内容在数据模型中可能多次出现，请使用元素，
    而不要引入名称类似 `foo1`、`foo2`、`foo3`
    .... 的属性。

2.  当某份信息可被视为独立对象，并且
    该信息通过父子关系与另一份信息
    相关联时，请使用元素来表示它。

3.  当数据涉及严格的类型或关系规则时，请使用元素。

4.  若两份数据之间的顺序很重要，请对它们使用元素：
    属性本质上是无序的。

5.  若某份数据具有、或可能具有自身的结构，请把它放在
    元素中：把子结构塞进属性总是很混乱。同样，
    若该数据是某个更大数据的组成部分，也请
    放在元素中。

6.  上一条规则的例外：多个以空白分隔的标记可以
    安全地放在属性中。原则上分隔符可以是任意字符，
    但模式语言的校验器目前只能处理空白，
    因此最好沿用空白。

7.  若某份数据跨越多行，请使用元素：XML
    解析器会把属性值中的换行符变成空格。

8.  若某份数据非常大，请使用元素，以便其内容可以
    被流式处理。

9.  若某份数据是自然语言，请把它放在元素中，以便
    使用 `xml:lang` 属性标注所用的语言。某些
    自然语言文本（如日语）常常使用
    [注解](https://www.w3.org/TR/2001/REC-ruby-20010531)，按惯例用子元素表示；
    而像希伯来语和阿拉伯语这类从右到左的语言，
    可能同样需要子元素来正确处理
    [双向性](https://www.w3.org/TR/2001/REC-ruby-20010531)。

<a id="s12.3"></a>

### 使用属性

1.  若数据是来自枚举、代码表或受控
    词表的代码，请尽可能放在属性中。例如语言标签、
    货币代码、医学诊断代码等最适合
    作为属性处理。

2.  若某份数据其实是关于另一份数据的元数据（例如
    表示主数据所承担的类或角色，或
    指定处理它的方法），请尽可能放在属性中。

3.  特别是，若某份数据是另一份数据的 ID，
    或是对该 ID 的引用，请把起标识作用的部分放在属性中。
    当它是 ID 时，请为该属性使用名称 `xml:id`。

4.  超文本引用按惯例放在 `href` 属性中。

5.  若某份数据适用于某元素及其任意后代元素，
    除非在其中某些元素上被覆盖，按惯例
    应把它放在属性中。众所周知的例子有 `xml:lang`、`xml:space`、`xml:base`，
    以及命名空间声明。

6.  若简洁真的*最*重要，请使用属性，但
    请考虑改用 `gzip` 压缩——它对具有高度重复结构的
    文档效果很好。

## 临别赠言

运用常识，并*保持一致*。为可扩展性而设计。你*确实*
会需要它。\[*理由：* 长期而痛苦的经验。\]

设计 XML 格式时，花几分钟看看其他格式，
并弄清它们的风格。制定风格准则的意义在于让人们
专注于你在说什么，而不是你怎样说。

打破*任意或全部*这些规则（是的，连写着 MUST 的规则也一样），
也不要因为盲目遵循它们而做出粗糙、随意、令人厌恶的
一团糟设计。尤其是，属性与子元素的随意混杂
既难理解也难使用，不过当数据明显分属
两个不同组（例如简单／复杂，或元数据／数据）时，
同时使用两者往往很合理。
