<a id="principles"></a>

## 风格原则

有几条总括性的原则，概括了应如何看待编写可读的 Go 代码。
以下按重要性顺序列出可读代码
的各项属性：

1.  **[清晰性][Clarity]**：代码的目的与原理对读者而言是清楚的。
1.  **[简洁性][Simplicity]**：代码以尽可能简单的方式
    达成其目标。
1.  **[简明性][Concision]**：代码具有较高的信噪比。
1.  **[可维护性][Maintainability]**：代码的编写方式使其易于
    维护。
1.  **[一致性][Consistency]**：代码与更广泛的 Google 代码库保持一致。

[Clarity]: #clarity
[Simplicity]: #simplicity
[Concision]: #concision
[Maintainability]: #maintainability
[Consistency]: #consistency

<a id="clarity"></a>

### 清晰性

可读性的核心目标是写出对读者而言清晰的代码。

清晰性主要通过有效的命名、有帮助的注释
以及高效的代码组织来实现。

清晰性应从读者的视角来衡量，而不是代码作者的视角。
代码易于阅读比易于编写更重要。代码中的清晰性有两个
不同的方面：

*   [代码实际在做什么？](#clarity-purpose)
*   [代码为什么要这样做？](#clarity-rationale)

<a id="clarity-purpose"></a>

#### 代码实际在做什么？

Go 的设计使得看清代码在做什么应当相对简单直接。在存在
不确定性的情况下，或当读者可能需要预先具备某些知识
才能理解代码时，值得投入时间，为未来的读者
把代码的目的讲得更清楚。例如，以下做法
可能有帮助：

*   使用更具描述性的变量名
*   补充额外的注释
*   用空白和注释把代码分隔开
*   把代码重构到独立的函数/方法中，使其更加模块化

这里没有放之四海而皆准的方法，但在开发 Go 代码时，
把清晰性放在首位很重要。

<a id="clarity-rationale"></a>

#### 代码为什么要这样做？

代码的原理通常已由变量、函数、方法或包的名称充分
传达。如果未能传达，补充注释就很重要。当代码中含有
读者可能不熟悉的细微之处时，「为什么」尤其
重要，例如：

*   语言本身的细微之处，例如闭包会捕获循环变量，
    但该闭包位于许多行之外
*   业务逻辑的细微之处，例如一项访问控制检查需要区分
    真实用户与冒充用户的人

某个 API 可能需要小心才能正确使用。例如，一段代码
可能出于性能原因而错综复杂、难以理解；又或者一连串
复杂的数学运算以出人意料的方式使用了类型转换。
在这些以及更多情况下，随附的注释和文档都
应解释这些方面，以免未来的维护者犯错，
也让读者无需反向工程
就能理解代码。

同样重要的是要意识到，某些提供清晰性的尝试（例如
添加额外注释）反而会掩盖代码的目的：它们带来杂乱、
重复代码已经表达的内容、与代码相矛盾，或增加维护
负担以使注释保持最新。应让代码自己说话（例如让
符号名称本身具有自描述性），而不是添加冗余注释。
注释通常更适合解释为什么做某事，
而不是代码在做什么。

Google 代码库大体上是统一且一致的。那些显得突出的代码
（例如使用了不常见的模式）往往有充分的理由，通常是
为了性能。保持这一特性很重要，它让读者在阅读一段
新代码时，能清楚知道应该把注意力
放在哪里。

标准库中有许多体现这一原则的实例。其中
包括：

*   以下位置的维护者注释：
    [`package sort`](https://cs.opensource.google/go/go/+/refs/tags/go1.19.2:src/sort/sort.go)。
*   优秀的
    [同一包中可运行的示例](https://cs.opensource.google/go/go/+/refs/tags/go1.19.2:src/sort/example_search_test.go)，
    这对用户（它们
    [会显示在 godoc 中](https://pkg.go.dev/sort#pkg-examples)）和维护者
    （它们[作为测试的一部分运行](decisions#examples)）都有好处。
*   [`strings.Cut`](https://pkg.go.dev/strings#Cut) 只有四行代码，
    但它们提升了
    [调用点的清晰性与正确性](https://github.com/golang/go/issues/46336)。

<a id="simplicity"></a>

### 简洁性

你的 Go 代码对使用、阅读和维护它的人来说都应是简单的。

Go 代码应以能达成其目标的最简单方式来编写，无论
在行为还是性能方面都是如此。在 Google 的 Go 代码库中，简单的
代码：

*   从上到下都易于阅读
*   不假定你已经知道它在做什么
*   不假定你能记住前面所有的代码
*   没有不必要的抽象层次
*   没有把注意力引向无关紧要事物的名称
*   让读者清楚地看到值与决策的传递
*   带有解释「为什么」而非「做什么」的注释，以避免日后
    出现偏差
*   拥有自成体系的文档
*   提供有用的错误信息和有用的测试失败信息
*   常常可能与「聪明」的代码互斥

代码简洁性与 API 使用简洁性之间可能出现权衡。
例如，让代码更复杂一些也许是值得的，这样 API 的最终
用户就能更容易地正确调用该 API。相反，把一点额外的
工作留给 API 的最终用户，以便代码保持简单、
易于理解，也可能是值得的。

当代码确实需要复杂性时，复杂性应当是有意加入的。
通常在需要额外性能、或某个特定的库或服务有多个
彼此差异很大的使用方时，才有此必要。复杂性也许是
合理的，但应附上相应的文档，让使用者和未来的
维护者能够理解并驾驭这种复杂性。此外还应辅以
展示其正确用法的测试和示例，尤其是当代码既存在
「简单」的用法，也存在
「复杂」的用法时。

这一原则并不意味着 Go 不能或不应编写复杂的代码，
也不意味着 Go 代码不允许变复杂。我们追求的是
一个避免不必要复杂性的代码库，这样当复杂性
真的出现时，它就表明相关代码需要小心
理解和维护。理想情况下，应随附注释解释其原理，
并指出需要注意之处。这种情况常出现在为性能
优化代码时；这样做往往需要更复杂的方式，
例如预先分配一个缓冲区，并在 goroutine 的整个
生命周期中重复使用它。维护者看到这一点时，
应把它当作一个提示：相关代码对性能至关重要，
而这会影响日后改动时应谨慎到何种程度。
另一方面，若毫无必要地采用这种复杂性，它就成为
未来需要阅读或修改代码者的负担。

如果代码的目的本应简单，结果却变得非常复杂，这
往往是一个信号：应重新审视实现，看看是否有更简单的
办法达成同样的效果。

<a id="least-mechanism"></a>

#### 最少机制

当有多种方式表达同一个想法时，优先选择使用最标准
工具的那一种。精巧的机制往往存在，但不应无端
采用。按需给代码增加复杂性很容易，而在发现既有
复杂性并无必要之后再将它移除，则要
困难得多。

1.  当核心语言构造足以满足你的用例时，尽量使用它
    （例如 channel、slice、map、循环或 struct）。
2.  如果没有，就在标准库中寻找工具（例如 HTTP
    客户端或模板引擎）。
3.  最后，在引入新的依赖或自行创建之前，先考虑
    Google 代码库中是否已有足够用的核心库。

举个例子，设想生产代码中有一个绑定到变量的 flag，
它带有默认值，而在测试中必须覆盖该值。除非打算
测试程序自身的命令行界面（比如用 `os/exec`），
否则直接覆盖绑定的值比使用 `flag.Set` 更简单，
因而也更可取。

类似地，如果某段代码需要做集合成员检查，布尔值的
map（例如 `map[string]bool`）往往就足够了。只有当
需要更复杂的操作、而用 map 无法做到或过于复杂时，
才应使用提供类集合类型与功能的库。

<a id="concision"></a>

### 简明性

简明的 Go 代码具有较高的信噪比。相关细节容易被
辨认出来，而命名与结构会引导读者
穿过这些细节。

有很多东西会妨碍在任何特定时刻凸显最
重要的细节：

*   重复的代码
*   多余的语法
*   [含义不明的名称](#naming)
*   不必要的抽象
*   空白

重复的代码尤其会掩盖各段几乎相同的代码之间的差异，
并要求读者逐行目视比对相似的代码行才能找出改动。
[表驱动测试][Table-driven testing] 就是一种能简洁地把公共代码
从每次重复的重要细节中抽离出来的机制，但选择把哪些
部分放进表里，会影响这张表
有多容易理解。

在考虑多种组织代码的方式时，值得想一想哪种方式
能让重要细节最为显眼。

理解并运用常见的代码构造与惯用法，对保持较高的
信噪比同样重要。例如，下面这段代码在[错误处理][error handling]中
非常常见，读者能很快理解
这段代码的用途。

<div class='goodcode'></div>

```go
if err := doSomething(); err != nil {
    // ...
}
```

如果代码看起来与此非常相似，却存在细微差别，读者
可能不会注意到这处变化。在这种情况下，值得有意
[「增强」]["boosting"] 错误检查的信号，比如添加注释引起注意。

<div class='goodcode'></div>

```go
if err := doSomething(); err == nil { // if NO error
    // ...
}
```

[Table-driven testing]: https://go.dev/wiki/TableDrivenTests
[error handling]: https://go.dev/blog/errors-are-values
["boosting"]: best-practices#signal-boost

<a id="maintainability"></a>

### 可维护性

代码被编辑的次数远多于被编写的次数。可读的代码不仅
要让试图理解其工作原理的读者看得懂，也要让需要
修改它的程序员看得懂。清晰性是关键。

可维护的代码：

*   便于未来的程序员正确修改
*   其 API 的结构能够从容地扩展
*   清楚说明所作的前提假设，并选择与问题结构相映射的
    抽象，而不是与代码结构相映射
*   避免不必要的耦合，不包含未被使用的功能
*   拥有全面的测试套件，以确保所承诺的行为得以保持、
    重要逻辑正确无误；并且在失败时，测试能提供清晰、
    可据以行动的诊断信息

使用接口、类型这类抽象时，按定义它们会移除所处
上下文中的信息，因此务必确保它们带来足够的
收益。当使用具体类型时，编辑器和 IDE 可以直接
跳转到方法定义并显示相应文档；但若使用接口，
就只能指向接口定义。接口是强大的工具，但也有
代价：维护者可能需要理解底层实现的细节才能
正确使用该接口，而这些细节必须在接口文档
或调用点
加以说明。

可维护的代码还会避免把重要细节藏在容易忽略的地方。
例如，在下面每一行代码中，某个字符的有无对于
理解该行都至关重要：

<div class='badcode'></div>

```go
// The use of = instead of := can change this line completely.
if user, err = db.UserByID(userID); err != nil {
    // ...
}
```

<div class='badcode'></div>

```go
// The ! in the middle of this line is very easy to miss.
leap := (year%4 == 0) && (!(year%100 == 0) || (year%400 == 0))
```

这两种写法都没有错，但都可以写得
更明确一些，或者附上注释以提醒读者注意
这一重要行为：

<div class='goodcode'></div>

```go
u, err := db.UserByID(userID)
if err != nil {
    return fmt.Errorf("invalid origin user: %s", err)
}
user = u
```

<div class='goodcode'></div>

```go
// Gregorian leap years aren't just year%4 == 0.
// See https://en.wikipedia.org/wiki/Leap_year#Algorithm.
var (
    leap4   = year%4 == 0
    leap100 = year%100 == 0
    leap400 = year%400 == 0
)
leap := leap4 && (!leap100 || leap400)
```

同样，如果辅助函数隐藏了关键逻辑或重要的
边界情况，日后的改动就可能很容易
没有恰当地把它考虑进去。

可预测的名称是可维护代码的另一项特征。包的使用者
或某段代码的维护者，在给定上下文中应当能预测
变量、方法或函数的名称。表示相同概念的函数参数
与接收者名称通常应使用同一个名字，这既让文档
易于理解，也便于以最小的开销
重构代码。

可维护的代码会尽量减少依赖（包括隐式和显式依赖）。
依赖更少的包，意味着可能影响行为的代码行数更少。
避免依赖内部行为或未文档化的行为，能降低这些行为
日后发生变化时带来维护负担的可能性。

在考虑如何组织或编写代码时，值得花时间想清楚
代码日后可能如何演进。如果某种做法更有利于
未来更轻松、更安全的改动，那往往是一次不错的
权衡，即便它意味着设计会稍微复杂一些。

<a id="consistency"></a>

### 一致性

一致的代码，是指在更广泛的代码库中、在团队或包
的上下文中、甚至在同一个文件内，其外观、感觉
和行为都与类似代码相仿。

对一致性的考量不会凌驾于上述任何原则之上，
但如果必须打破平局，向一致性倾斜往往是有益的。

包内的一致性往往是最直接、最重要的一致性层次。
如果同一个问题在整个包里以多种方式处理，或者
同一个概念在一个文件中有许多名称，都会令人
非常不适。不过，即便如此，它也不应凌驾于
成文的风格原则或全局一致性之上。

<a id="core"></a>

## 核心指南

这些指南汇集了所有 Go 代码都应遵循的、关于 Go 风格
最重要的方面。我们希望到获得可读性认证时，
这些原则已被学习并遵循。预计它们不会频繁变动，
新增内容必须跨过很高的门槛。

下面的指南扩展了 [Effective Go] 中的建议，它们为
整个社区的 Go 代码提供了共同的基线。

[Effective Go]: https://go.dev/doc/effective_go

<a id="formatting"></a>

### 格式

所有 Go 源文件都必须符合 `gofmt` 工具输出的格式。
该格式由 Google 代码库中的预提交检查强制执行。
[生成的代码][Generated code] 通常也应进行格式化（例如使用
[`format.Source`]），因为它在 Code Search 中同样可被浏览。

[Generated code]: https://docs.bazel.build/versions/main/be/general.html#genrule
[`format.Source`]: https://pkg.go.dev/go/format#Source

<a id="mixed-caps"></a>

### MixedCaps

编写多词名称时，Go 源代码使用 `MixedCaps` 或 `mixedCaps`
（驼峰式），而不是下划线（蛇形式）。

即使这会打破其他语言的约定，也同样适用。例如，
一个常量在导出时是 `MaxLength`（而非 `MAX_LENGTH`），
在未导出时是 `maxLength`（而非 `max_length`）。

在选择首字母大写方式时，局部变量被视为
[未导出][unexported]。

> **注意：**以下内容不受此规则约束：
>
> *   生成的 Protocol Buffer API
> *   标准库面向操作系统的接口，例如
>     https://pkg.go.dev/syscall#pkg-constants
>
> **人工编写的代码适用更高的标准。**

[unexported]: https://go.dev/ref/spec#Exported_identifiers

<a id="line-length"></a>

### 行长度

Go 源代码没有固定的行长度限制。如果某一行显得过长，
优先选择重构，而不是把它拆开。如果它已经短到
实际可行的极限，就应允许该行保持较长。

不要在以下情况拆分一行：

*   在[缩进变化](decisions#indentation-confusion)之前（例如函数声明、
    条件语句）
*   为了让长字符串（例如 URL）能放进多个较短的行

<a id="naming"></a>

### 命名

命名与其说是科学，不如说是艺术。在 Go 中，名称往往比
许多其他语言略短，但同样的[通用指南][general guidelines]适用。名称应当：

*   在使用时不显得[重复](decisions#repetition)
*   把上下文纳入考量
*   不重复已经清楚的概念

关于命名的更具体指导，可参见[决策](decisions#naming)。

[general guidelines]: https://testing.googleblog.com/2017/10/code-health-identifiernamingpostforworl.html

<a id="local-consistency"></a>

### 局部一致性

当风格指南对某个具体的风格问题未作规定时，作者
可以自由选择自己偏好的风格，除非邻近的代码
（通常在同一文件或包内，有时在同一团队或
项目目录内）已对该问题采取一致的立场。

**有效**的局部风格考量示例：

*   在格式化输出错误时使用 `%s` 或 `%v`
*   使用带缓冲的 channel 代替互斥锁

**无效**的局部风格考量示例：

*   对代码设置行长度限制
*   使用基于断言的测试库

如果局部风格与风格指南相左，但对可读性的影响
仅限于一个文件，通常会在代码评审中被指出；而
一致的修复往往超出当前 CL 的范围。此时，
提交一个 bug 来跟踪该修复是合适的。

如果某项改动会加剧既有的风格偏差、让它在更多 API
表面暴露出来、扩大出现该偏差的文件数量，或引入
真正的缺陷，那么局部一致性就不再是新代码违反
风格指南的有效理由。在这些情况下，作者应
在同一个 CL 中清理现有代码库，在当前 CL 之前
先行重构，或找到至少不会让
局部问题恶化的替代方案。
