## 最小可行文档

少量新颖而准确的文档，胜过一大堆
处于各种失修状态的“文档”。

编写简短而有用的文档。删掉一切不必要的东西，包括
过时、错误或冗余的信息。还要养成
不断打磨和改进每份文档、以适应不断变化需求的习惯。
**文档保持活力但经常修剪时效果最好，就像一株
盆景**。

另请参见
[这些敏捷文档最佳实践](https://www.agilemodeling.com/essays/agileDocumentationBestPractices.htm)。

## 随代码一起更新文档

**在代码变更的同一个 CL 中更新你的文档**。这能让你的
文档保持新鲜，也是向评审者解释你在
做什么的好地方。

一位好的评审者至少可以坚持要求 docstrings、头文件、README.md
文件以及任何其他文档都随 CL 一起更新。

## 删除失效文档

失效文档很糟糕。它们误导人，拖慢进度，让工程师
陷入绝望、让团队负责人变得懈怠。它们开创了在代码库中
留下烂摊子的先例。若你的家是干净的，多数客人不用
被要求也会保持干净。

就像任何大型清扫项目一样，**很容易让人不知所措**。若你的
文档状况很糟糕：

*   慢慢来，文档健康是逐步积累的。
*   先删除你确定有误的内容，忽略不清楚的部分。
*   让整个团队参与进来。花时间快速浏览每份文档并做出
    简单的决定：保留还是删除？
*   迁移时默认删除或留下不管。掉队的内容总能
    被找回。
*   反复迭代。

## 宁求其好，不求其完美

文档是一门艺术。没有完美的文档，只有经过验证的
方法和审慎的准则。参见[好优于最好](./style.md)。

## 文档是你的代码的故事

写出优秀的代码并不止于代码能编译、甚至不止于测试
覆盖率达到 100%。写出计算机能理解的东西很容易，
写出人和计算机都能理解的东西则难得多。作为
一名注重代码健康的工程师，你的使命是**先为人而写，
其次才是计算机。**文档是这项能力的重要部分。

工程文档存在一个从简略注释
到详尽论述的光谱：

1.  **有意义的名称**：良好的命名能让代码传达本会
    被归入注释或文档的信息。这包括
    各个层次可命名的实体，从局部变量到类、文件和
    目录。

2.  **行内注释**：行内注释的首要作用是提供
    代码本身无法包含的信息，例如代码为何
    存在。

3.  **方法注释与类注释**：

    *   **方法 API 文档**：说明方法做什么以及如何使用的
        头部 / Javadoc / docstring 注释。这类文档是
        **你的代码必须如何行为的契约**。目标读者是
        将来使用和修改你代码的程序员。

        通常可以合理地认为，此处记录的任何行为都应
        有测试加以验证。这类文档详述方法接受哪些参数、
        返回什么、有哪些“坑”或限制，以及
        可能抛出哪些异常或返回哪些错误。它通常
        不解释代码为何以某种方式运行，除非这与
        开发者理解如何使用该方法有关。“为何”的解释
        属于行内注释。编写方法文档时请从实用角度考虑：
        “这是一把锤子，你用它来敲钉子。”

    *   **类 / 模块 API 文档**：头部 / Javadoc / docstring
        针对某个类或整个文件的注释。这类文档简要
        概述该类 / 文件做什么，并常给出几个简短
        示例，说明可以如何使用该类 / 文件。

        当存在若干种截然不同的使用方式时，示例
        尤其重要（有的高级，有的简单）。始终首先列出最简单的
        用例。

4.  **README.md**：一份好的 README.md 能让新用户熟悉该目录，并
    指向更详细的说明和用户指南：

    *   这个目录打算存放什么？
    *   开发者应该先看哪些文件？其中有些文件是 API 吗？
    *   谁维护这个目录，我在哪里可以了解更多？

    请参见 [README.md 准则](READMEs.md)。

5.  **docs**：一个好的 docs 目录中的内容会说明如何：

    *   开始使用相关的 API、库或工具。
    *   运行它的测试。
    *   调试它的输出。
    *   发布二进制文件。

6.  **设计文档、PRD**：一份好的设计文档或 PRD 会详细讨论
    拟议的实现，目的是就该设计收集反馈。
    然而，一旦代码实现，设计文档应作为
    这些决策的档案，而非半对半错的文档（它们常常
    被误用）。

7.  **其他外部文档**：有些团队在代码之外的其他
    位置维护文档，例如 Google Sites、Drive 或 wiki。若
    你确实在其他位置维护文档，应从项目目录清楚地指向
    那些位置（例如，通过从项目的
    `README.md` 中添加一个指向该位置的醒目链接）。

## 重复是万恶之源

不要为常见的 Google 技术或流程另写一份自己的指南。请链接到它。
若该指南不存在或严重过时，请把你的
更新提交到相应的目录，或创建包级 README.md。**主动
承担起来，别不好意思**：其他团队通常会欢迎你的
贡献。
